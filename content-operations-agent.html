Turning content standards into an AI-assisted publishing workflow

A Claude Code agent for the Royal Borough of Greenwich digital team that processes content change tickets into a structured work pack: updated content, a change summary, Drupal instructions and a draft reply.

PROJECT ARTEFACT / Content Operations Agent
CONTENT REQUEST “Can you update this page?”↓Clarify → Draft → Check↓✓   Human review
Role
Content design, agent design
Tools
Claude Code, VS Code, Drupal, SharePoint, Freshservice
Context
Royal Borough of Greenwich digital team
Evidence
12 anonymised historical tickets

The hard part was not getting an LLM to rewrite content. It was deciding which content-design judgements could be made explicit enough for a system to apply, and which still need a person.

The situation

The Content Design team runs content operations for the council's website. Requests come in from services across the council: updating a page, creating a friendly link, archiving a page, creating a new section. Every ticket needs the same sequence of decisions: read the brief, identify whether the page is public-facing or on the intranet, apply the style guide, rewrite the content, generate any Drupal instructions, and reply to the requester.

The problem

Completing a ticket properly involves several separate decisions:

  • understanding exactly what the requester wants changed
  • checking whether the page is public-facing or on the intranet
  • applying the correct writing and accessibility standards
  • understanding how the change should be made in Drupal or SharePoint
  • spotting risks such as reusable components, page deletion or conflicting instructions
  • writing a clear response back to the requester

The knowledge needed was spread across style guidance, publishing rules, accessibility conventions and practical platform knowledge. So the difficult part was turning an often incomplete ticket into a safe, publishable change without losing the intent of the request.

Goal 1

Apply content standards consistently. Review content against defined standards rather than ad-hoc prompting.

Goal 2

Turn standards into actionable decisions. Explain why a problem matters and recommend changes while preserving the author's intent.

Goal 3

Reduce repetitive operations. Create a repeatable AI-assisted workflow for reviewing, rewriting and preparing content.

Decisions

1. Set the boundaries before the style rules

Content operations is not content design. I scoped the agent as an operations processor, not a strategist or designer: it processes what is in the ticket, no more and no less. This protects against the most common failure of AI content tools, confident overreach. An agent that rewrites more than it was asked to, or guesses at an ambiguous brief rather than flagging it, creates work instead of reducing it. The guardrails were written first because they define the agent's character.

2. Detect context from the data, not from extra instructions

The same request needs different rules depending on where the page lives. A URL containing sharepoint.com triggers intranet rules and SharePoint ownership checks. A URL containing royalgreenwich.gov.uk triggers public-facing rules and Drupal/GOV.UK conventions. This one decision removes a whole class of errors, wrong rules on the wrong platform, without asking the editor to say so on every ticket.

3. Make the style guide operational, not aspirational

I converted the team's institutional knowledge into explicit agent instructions so the agent never has to rely on vague model knowledge. Rules include plain English at reading age 9, active voice, one idea per paragraph, no adverbs, accessible link text, spelled-out negatives, no exclamation marks and no FAQs. The jargon substitution list is explicit: utilise → use, commence → start, ensure → make sure, in the near future → soon. Claude helped me structure and articulate rules that already existed; I reviewed and refined them.

4. Separate behaviour from knowledge

The system prompt tells the agent how to behave and make decisions. The guidance files (the Greenwich style guide, Drupal publishing guidance, SharePoint intranet guidance, common-task instructions such as creating a friendly URL) provide the reference it works through. Keeping those layers separate means guidance can be updated without redesigning the agent's behaviour.

5. Don't stop at "here is the content change"

Many requests involve URLs, redirects, page structures, documents and publishing status. The agent gives step-by-step Drupal guidance alongside its content recommendation: friendly links, URL aliases and redirects, landing and guide pages in the right order, page status, replacing documents, reusable components, and checking archived content is no longer public. The content designer learns how to implement the change safely, not just what to change.

6. A fixed output architecture for every ticket

  1. Ticket summary: what has been requested, which page is affected and the type of change
  2. Rewritten or updated content: publication-ready, with standards applied
  3. Change summary: what changed, why, and which rule was used
  4. Step-by-step Drupal instructions: only where the change needs CMS actions
  5. Draft ticket reply: ready to paste into Freshservice

This separates the content decision, its rationale, the implementation steps and the communication back to the requester, so there is less to interpret before acting.

Using Claude at three stages

As a drafting tool: I supplied standards, Drupal procedures and operational rules, used Claude to structure them into a system prompt, then refined the result so rules were explicit and boundaries clear. As a testing tool: I ran real ticket scenarios against successive prompt versions and looked for unnecessary rewriting, incorrect Drupal guidance, missing information and over-long responses. As the runtime: Claude Code became the interface through which tickets are processed against the system instructions.

Results from 12 tested tickets

I tested the agent against 12 anonymised historical tickets of varying complexity, measuring completion time, number of revisions, rule-compliance errors, Drupal instruction errors and acceptance rate.

What I learned

  • Rules need to be operational, not aspirational. "Write clearly" produced inconsistent behaviour. The agent performed better when standards were translated into specific decisions, conditions and examples.
  • Failure cases were more useful than successful outputs. Incorrect Drupal instructions and unnecessary rewriting exposed gaps in the instructions and became regression-test scenarios.
  • Consistency does not remove the need for judgement. The agent can interpret tickets and prepare guidance, but the content designer remains responsible for context, exceptions and the final publishing decision.

What I would do next

Move from a prompt-led prototype to a maintainable content-operations system:

  • expand the evaluation set across more ticket types and edge cases
  • maintain a regression suite so previous failures are retested after prompt changes
  • separate frequently changing Drupal procedures from the core system instructions
  • introduce versioning for rules and evaluation results
  • test where structured tools or deterministic workflows are safer than LLM reasoning
  • explore integration with the ticketing workflow while retaining human approval before publication

Ticket screenshots and internal documents are withheld for confidentiality. Test sample was 12 tickets, so treat results as indicative of a prototype rather than a production benchmark.
