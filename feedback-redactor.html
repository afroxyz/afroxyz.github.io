Case study 06 · HTML · JavaScript · Privacy by design

A privacy tool that had to pass its own test

To analyse resident feedback with AI, you first have to strip the personal data out of it. So I built a redactor that does that entirely in the browser — the file never leaves the machine. Then I did the part most tools skip: I tried to break it against a real export, and it told me exactly where a privacy promise was resting on a guess.

A redactor is a promise: nothing personal gets through. A promise you have never tried to break is the most dangerous kind — so the tool is only half the work. The other half is proving it keeps the promise, and finding where it doesn't.

Why I built it

Resident feedback is one of the richest sources a council has, and one of the most sensitive. People leave names, phone numbers, addresses, case references — sometimes details about their health or their children — in a free-text box meant for "tell us what went wrong". None of that can go anywhere near an AI tool for analysis until it has been removed.

Doing that by hand across thousands of comments doesn't scale and isn't safe: a tired person misses things. And the data itself shouldn't have to leave council-controlled systems just to be cleaned. So I built a redactor with one firm rule — the file never leaves the browser. It opens, redacts and checks the export on the machine it's already on; nothing is uploaded, sent or stored. Close the tab and it's gone.

What it does

It walks through four steps. You choose the feedback file; you decide what happens to each column; you review a list of possible names it couldn't be certain about; and you check the result before downloading a clean copy.

Underneath, two things are working together. A set of pattern detectors catches the things that have a shape — emails, phone numbers, postcodes, National Insurance numbers, addresses, reference numbers. And because names don't have a shape, a name-finder — word lists plus a small language model running in the browser — flags likely names for a human to confirm, so the person stays in control of the judgement calls. A final screen re-checks the output and previews what changed.

Why I evaluated it

Everything else I build, I can fix after the fact. A redactor is different: if it lets one real address or phone number through into a file that then gets shared or analysed, the harm is already done, and no amount of "it usually works" undoes it. A privacy tool you trust without testing isn't a safeguard — it's a liability wearing the costume of one.

So I treated "built" and "verified" as two different states. I took a real feedback export, ran it through the tool, and read the output line by line against what should and shouldn't still be there — not to confirm it worked, but to find where it didn't.

What the evaluation found

Against one real export — a "report a problem" form, 331 rows — the tool was strong where I'd spent the most effort: an automated re-scan of the output found no emails, phone numbers, postcodes, National Insurance numbers or long numbers left in the free text. The hard part, cleaning what residents type, held up.

The gaps were in two places I'd paid less attention to, and together they taught me more than the passes did.

  • Personal data hiding in structured columns. The export carried columns the free-text detectors were never meant to clean — IP addresses, staff account IDs and links, and in one column a lone first name while other cells in it had been redacted. Machine-generated identifiers and a single out-of-the-ordinary name are exactly what pattern-matching and name lists miss.
  • Over-redaction of data that wasn't personal. Redaction can fail in two directions. Timestamps the analysis actually needs — created, completed, changed — were being chewed into tokens, destroying non-personal data the report depends on. A redactor that mangles your dates is as broken as one that leaks an address, just less dangerously.

And the quiet structural problem underneath both: a file could end up labelled "redacted-checked" without anything actually having to pass a check. The reassurance was in the filename, not earned by the tool.

One honest caveat made the lesson sharper. The export's own settings had changed between runs — an earlier version had no IP-address column and readable dates — so some of this traced not to a broken detector but to the tool leaning on guesses about which columns were safe. When the shape of the data shifted, the guesses did too. That is the whole finding in miniature: a safeguard resting on a heuristic is a safeguard waiting for the input to change.

The fix I specified

The evaluation didn't just list faults; it defined the safer design, so the same failures become impossible rather than unlikely.

  • Handle columns first, from an explicit allowlist. Every column gets one of three fates — keep, redact as free text, or drop — decided by name before any text matching runs. Anything not on the list is dropped by default, so a new column added to the export can't quietly slip through.
  • Run detectors only on free-text columns. Timestamps, IDs and URLs never touch the free-text redactor, which stops a date being eaten as a number and keeps the fields the analysis needs.
  • Order the patterns. Match the most specific things first — IP addresses before dates and numbers — so one detector can't swallow half of another's match.
  • Widen the net to the identifiers this data actually contains: IP addresses, council-tax and case references, and URLs carrying account IDs.
  • Add a gate that blocks the download. After redaction, a separate step re-scans the output and fails the export if any non-allowed column survives or any pattern still matches — reporting column names and row numbers only, never the values, so the audit itself holds no personal data.
  • Let the tool earn the label. The "redacted-checked" name is applied by the tool only when that gate passes — never typed by hand.
  • Keep a person in the loop for free text, because a name written in plain words can't be caught reliably by any rule.

Each fix comes with test cases built from made-up values, checking both what must be removed and what must survive — so the gains can be proven and kept, not just claimed once.

What I learned — for this tool and the next

  • Safety has to be structural, not a guess. Deciding column fates from an explicit list — and dropping the unknown by default — is safe when the data changes. A heuristic that reads the columns and infers what's personal is only safe until the export does something new.
  • Redaction is two failures, not one. Leaking real personal data is the obvious one. Destroying non-personal data the analysis depends on is the quiet one — and a tool has to be judged on both.
  • A guarantee must be earned, not asserted. "Redacted-checked" belongs in a filename only when a check has actually run and passed. A label is not a safeguard.
  • Make the audit safe too. Report findings as column names and row numbers, never values, so the act of checking for personal data never creates another copy of it.
  • Evaluate against real, messy exports. Every gap here came from real data doing something a tidy test file wouldn't — an unexpected column, a changed export setting, a name from outside the lists. Clean test data would have passed and taught me nothing.

What I would improve

  • Build the allowlist and the validation gate, then run them over both existing exports to confirm the gaps close.
  • Add the test cases to a suite that runs on every change, so a future edit can't silently reopen a gap.
  • Confirm with the export's owner why the columns changed between runs — the tool can only be as safe as the data it's handed.
  • Check the blast radius: find whether other form exports go through the same tool and share the same gaps.
  • Fold the gate into the shared standard, so every redaction tool in the wider system inherits "re-scan the output and earn the label" rather than reimplementing it.
