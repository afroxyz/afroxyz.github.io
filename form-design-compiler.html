The project in brief

The Digital Forms Team builds Drupal Webforms that combine field types, page structure, conditional states, error messages, file uploads and review pages. Much of the knowledge needed to build them consistently lived in people’s heads.

I made that knowledge explicit in a structured system prompt and reusable conventions, then used a Claude workflow in VS Code to generate form YAML from requirements or design inputs. I built the workflow and continue to refine it. Content decisions, accessibility testing and deployment remain human-owned.

The professional judgement came first

The design work was to decide what a correct form should look like before asking a model to produce it. That included selecting field types, naming machine keys, writing useful errors, handling conditional requirements and deciding which recurring patterns should be used.

A generated form can be syntactically plausible and still ask an irrelevant question, hide the wrong content or demand an answer from someone who should not have to provide it. The rules therefore need to describe behaviour as well as output format.

The core artefact is system-prompt.md in a VS Code project. I encoded rules for raw YAML output, standard navigation elements, machine-key conventions, field-specific error patterns, conditional required states, address and upload patterns, repeatable elements, and the check-your-answers page.

I also configured a Figma-reading path and a Microsoft 365 Copilot version using the same design knowledge, supporting different inputs and ways for the team to access the workflow.

Four decisions that made the knowledge reusable

1. Give machine keys a convention

Early output used inconsistent or overly long keys and could collide with reserved names. I encoded a type-prefix and short-summary convention, a prefix table, disambiguation rules and a maximum summary length.

The aim is predictable keys that people can inspect and relate to the source field. Encoding that intention in a prompt does not guarantee collision-free output; it gives reviewers a clear rule against which to check it.

2. Make conditional requirements an explicit pattern

The project encountered generated fields combining a static required property with a conditional required state. The intended behaviour was for a field to be required only on a relevant branch.

I documented the permitted pattern and the conflicting combination to avoid. Reviewers still need to exercise both the visible and hidden branches in Drupal; an instruction is not a substitute for a runtime check.

3. Derive the review page from the form

Each source field needs the appropriate preview element and reference on the check-your-answers page. The review item also needs the relevant visibility conditions, including conditions inherited from a parent page.

Generating that structure from the form makes the relationship explicit. A review page should reflect the route the person actually took, rather than exposing answers or sections that do not apply.

4. Encode discovered failures as named controls

Repeating composite elements were a specific implementation problem. During development, conventional name selectors failed where field names were dynamically indexed. I added a tested selector pattern using data-drupal-selector to the instructions.

Declarations became discretionary rather than being inserted into every form. Upload and other recurring patterns were also documented. The value is in turning a discovered failure into knowledge the next generation and review can use.

Inspect the failure-and-fix examples

Expand each development finding to see the encoded response and the check that remains necessary.

Inconsistent machine keys

Observed: keys varied in structure or conflicted with reserved names.

Encoded response: a type-prefix mapping, short-summary convention and disambiguation rules.

Review: inspect naming and check uniqueness before import.

Required fields on an irrelevant branch

Observed: static and conditional required rules were combined.

Encoded response: use the appropriate conditional pattern when an answer is required only in a relevant state.

Review: test the positive and negative branches, including hidden fields.

Review items without their source conditions

Observed: early check-your-answers output exposed items regardless of the route taken.

Encoded response: mirror relevant conditions from the source field or parent page.

Review: compare the preview against multiple completed paths.

Declarations added when they were not requested

Observed: the agent inserted a declaration page by default.

Encoded response: make the declaration pattern explicit and discretionary.

Review: confirm the service requirement rather than accepting a generated convention automatically.

Consistency as a reviewable system

A shared prompt makes standards available across generated forms: the same field catalogue, naming rules, error patterns and review-page conventions. Versioning makes changes to that knowledge inspectable.

This supports consistency and adherence to the team’s agreed standards. It does not establish regulatory compliance, error-free generation or identical model behaviour on every run. Service eligibility and policy decisions remain with the responsible people.

What is demonstrated and what remains unmeasured

The documented achievement is a built workflow, a structured knowledge source and specific development failures translated into corrective rules. The material does not include a reproducible benchmark, matched timing study or published regression-test results.

I therefore do not turn the source’s qualitative time-saving description into a percentage saving or a claim that all logic errors are caught before testing. A stronger evaluation would measure first-pass import success, conditional-behaviour correctness, review-page coverage, revision effort and total build-and-review time across a representative form set.

Reflection and evidence notes

The most important part of the system is the design knowledge it distributes. Generation is useful when that knowledge is explicit, output can be inspected, and a person retains responsibility for the service being built.
